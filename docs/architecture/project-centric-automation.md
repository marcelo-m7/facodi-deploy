# FACODI Project-Centric Automation Architecture

Status: proposed direction, 2026-10-07.

This document is the canonical direction for the next FACODI automation increments.
Where older plans describe a separate technical workflow as the primary operational
model, this document supersedes that interpretation. Historical audit evidence
remains valid as evidence, but not as the target product architecture.

## 1. Product principle

FACODI should be **Odoo-standard first**.

Operational work visible to humans, collaborators and future portal users should
live primarily in Odoo Community's standard **Project** application:

- `project.project` is the long-lived operational workspace;
- `project.task` is the visible unit of execution/work;
- stages, task state, assignees, dependencies, activities, chatter, followers,
  attachments, deadlines and portal access remain standard Odoo mechanisms;
- FACODI extends these models only with the minimum machine-readable identity and
  automation metadata that Odoo does not already provide.

Supabase remains the technical processing plane for expensive/background AI and
metadata work. Odoo remains the operational/product system of record.

## 2. Current problem to remove

The current code evolved through several parallel mechanisms:

- FACODI Learning owns content-domain records plus analysis jobs/results,
  submission lifecycle, candidate lifecycle and workflow UI;
- FACODI API owns pipeline run/step/artifact records and mirrors them into Project;
- historical FACODI AI adds another provider/request/prompt/runtime abstraction;
- Project currently contains generated projects/tasks that mirror technical runs;
- the Theme occasionally carries product-flow presentation that depends on these
  custom mechanisms.

This creates too many state machines for a small team.

Production currently contains long-lived projects `FACODI` and
`FACODI Ingestão & Conteúdos`, but also generated projects named
`FACODI Pipeline <uuid>` with a parent content task plus three technical step
tasks. The latter is transitional evidence, not the desired end state.

## 3. Target model

### 3.1 Long-lived Projects, not one Project per execution

Use a small set of stable projects, for example:

- FACODI — Product & Community
- FACODI — Content Operations
- FACODI — Experiments & Automation

An execution creates/reuses a **task**, not a new project.

Technical pipeline stages are not automatically represented as three Project
subtasks. A subtask exists only when it is useful to a human, collaborator or
portal user. Technical checkpoints remain in Supabase/API logs and are summarized
on the parent task.

### 3.2 Minimal extensions to `project.project`

Introduce a small addon, provisionally named `facodi_project`, that inherits the
standard Project models.

Initial project fields:

- `facodi_ref` — immutable FACODI reference for integrations/imports;
- `facodi_managed` — marks a Project as participating in FACODI automation;
- `facodi_kind` — coarse workspace role such as content, automation,
  experiments, community;
- `facodi_automation_mode` — `auto`, `exception`, or `manual`, default
  `auto` for FACODI-managed projects.

Do not duplicate portal visibility, followers, task dependencies, milestones,
activities, chatter, task properties, access tokens or standard task state.

### 3.3 Minimal extensions to `project.task`

Initial task fields:

- `facodi_ref` — immutable unique execution/work reference generated by FACODI;
- `facodi_external_ref` — optional external receipt/job UUID, e.g. Supabase;
- `facodi_idempotency_key` — stable replay key;
- `facodi_kind` — ingestion, analysis, experiment, publication, sync or other
  controlled values;
- `facodi_origin` — submission, API, scheduled automation, manual, etc.;
- a safe target reference to the Odoo business object when required.

Use standard Project fields for the human-visible lifecycle:

- `stage_id` and `state` for progress/decision;
- assignees and followers for responsibility;
- activities for exceptions requiring a person;
- chatter for concise execution receipts and decisions;
- attachments for human-readable evidence;
- parent/subtasks and dependencies only when they represent real work.

A stable reference must never depend on the task name. Renaming a task must not
break replay or correlation.

## 4. Automation policy: autonomous by default

FACODI currently has few collaborators. The default policy therefore changes from
"human review for every machine proposal" to **automatic execution and approval
when guardrails pass, human work by exception**.

Default behavior for a FACODI-managed project:

1. intake creates or reuses an idempotent task;
2. Supabase/API performs metadata/AI processing;
3. deterministic validation evaluates the output;
4. if confidence, provenance and policy checks pass, the result is accepted
   automatically;
5. publication is also automatic when the project's publication policy and
   safety/quality gates pass;
6. the task is moved to the appropriate approved/done stage and a concise receipt
   is posted to chatter;
7. if a gate fails or confidence is insufficient, the task becomes an exception:
   assign/create an activity for a human and do not publish.

This same model applies to experiments: run automatically, record evidence,
promote/approve automatically when explicit success criteria pass, otherwise
open a human exception task.

Auto-approval must be explainable and policy-driven. It is not permission to
ignore source provenance, duplicate detection, licensing/visibility rules,
security failures or explicit manual locks.

## 5. Ownership by addon

### `facodi_project` — new small standard-extension addon

Owns:

- Project/Task FACODI reference fields;
- Project automation defaults/policies;
- execution/task correlation;
- generic Project UI additions and settings;
- portal-safe Project/Task increments that are domain-neutral;
- helpers for creating/reusing FACODI-managed tasks idempotently.

It should be small and depend on standard `project`/portal/mail capabilities
rather than recreating them.

For now it can live in the `facodi-api` repository as an independent Odoo addon,
avoiding another repository/gitlink while keeping source ownership separate at
module level.

### `facodi_api`

Target responsibility:

- authenticated API/webhook boundary;
- provider dispatch/adapters;
- Supabase execution integration;
- idempotent orchestration helpers;
- compatibility during migration.

The current `facodi.pipeline.run/step/artifact` state machine is transitional.
New features should not expand it. Migrate correlation and operational status to
Project tasks incrementally, while technical processing evidence remains in
Supabase.

### `facodi_learning`

Target responsibility:

- `slide.channel` / `slide.slide`;
- curricula, curriculum units, coverage and semantic/course relations;
- learning-specific source metadata and application of approved AI results.

Move generic execution workflow, technical retries, experiment lifecycle and
generic review orchestration out of Learning.

Submission/candidate/analysis models are migration targets, not all immediate
deletions. First link them to the canonical Project task, then shrink or retire
the duplicated lifecycle only after portal/UI parity exists.

### `theme_facodi`

Theme owns presentation only:

- visual components;
- website layout;
- public navigation/branding.

It must not own pipeline state, orchestration, approval rules or provider logic.

### `facodi_ai` and `facodi_ai_learning`

Do not build new FACODI product behavior on `facodi_ai_learning`.

Recommended direction:

- freeze `facodi_ai_learning` and migrate any still-useful FACODI behavior to
  Supabase + Project;
- keep generic `facodi_ai` temporarily as an optional reusable Odoo AI addon;
- FACODI core must not depend on it;
- after an inventory proves no unique FACODI runtime dependency remains,
  uninstall/retire `facodi_ai_learning`;
- decide separately whether generic `facodi_ai` is worth maintaining as a
  reusable non-FACODI module.

Supabase Edge is the primary AI execution plane for FACODI.

## 6. UI and configuration direction

Expose FACODI automation where Odoo users already expect it.

Project form:

- FACODI reference;
- workspace kind;
- automation mode;
- future publication/experiment policy options.

Task form/kanban:

- FACODI execution reference;
- external execution receipt;
- kind/origin;
- related business object;
- concise last automation outcome;
- retry/re-run only when technically meaningful;
- human-review buttons only for exception-mode tasks.

Settings should provide global defaults, while each managed Project may override
them. Avoid a separate FACODI technical dashboard when standard Project kanban,
filters, activities and reporting can express the same information.

Portal evolution should extend standard Project/Task portal access instead of
creating another parallel portal. Only safe fields and chatter should be exposed.

## 7. Migration sequence

### Increment 1 — Project identity foundation

Create `facodi_project` with the minimal Project/Task fields and idempotent task
helper. No deletion of old models. No broad pipeline cutover.

This increment is greenfield: preserve old Projects/tasks passively, without
adoption, ref backfill or changes to followers, stages, assignees, chatter or
history. No preliminary archive/delete is required. Task19 is ordinary work
tracking, not a special fixture. Legacy dispatch is untouched until Increment2
and must not be adapted or expanded in Increment1. Workspace `auto` is inert
metadata here: no processing, approval or publication is activated.

Acceptance:

- unique stable refs;
- every new Increment1 helper/code path forbids a Project per execution and
  compulsory technical subtasks; this does not cut over old dispatch;
- standard Project UI displays automation metadata;
- upgrade preserves all existing Projects/Tasks.

### Increment 2 — New executions use canonical tasks

Route new API/Supabase work to one canonical `project.task` per execution.
Existing `facodi.pipeline.run` may remain as compatibility evidence but must
reference the task rather than creating a new Project + mirrored technical steps.

Acceptance:

- replay reuses the same task;
- Supabase job UUID is correlated to the task;
- technical steps do not create Project subtasks unless human-actionable;
- failures create an activity/exception rather than a second workflow.

### Increment 3 — Automatic decision policy

Add project-level automation policy, default `auto`.

Acceptance:

- safe cases auto-approve;
- safe publication can complete without a human click;
- guardrail failure routes to exception/manual review;
- every automatic decision writes a concise policy/evidence receipt;
- manual lock/override always wins.

### Increment 4 — Learning workflow reduction

Move generic analysis/approval execution out of Learning. Link current
submission/source/candidate records to their Project task, then retire duplicate
technical job state where parity is proven.

Acceptance:

- learning models retain learning-domain facts;
- Project owns operational workflow;
- Supabase owns technical processing detail;
- no loss of existing portal tracking or editorial history.

### Increment 5 — Portal Project expansion

Extend standard Project/Task portal features for contributors/collaborators.

Acceptance:

- portal users see only authorized tasks/projects;
- submission/contribution status is represented through the same task lifecycle;
- no technical payloads/secrets/provider configuration leak.

### Increment 6 — AI addon decision and cleanup

Inventory `facodi_ai` and `facodi_ai_learning`.

Default outcome for FACODI:
`facodi_ai_learning` retired; generic `facodi_ai` optional or independently
maintained.

## 8. Release discipline

Each increment is independently releasable:

1. owner addon PR with migration/tests;
2. exact gitlink pin in `facodi-deploy`;
3. clean-install + upgrade + browser/runtime gates;
4. production rollout;
5. MCP read-only verification of installed version/data;
6. one controlled canary when behavior changed;
7. only then start the next increment.

Do not bundle Project migration, portal redesign, AI retirement and publication
automation into one release.

## 9. Explicit non-goals for the first increment

Do not yet:

- delete existing pipeline/analysis/submission history;
- activate all old pipeline crons/gates;
- migrate every Learning model at once;
- create a second LMS;
- create one Project per execution;
- duplicate standard Project portal/security/chatter/activity functionality;
- make the Theme an orchestration owner.

The first implementation should be deliberately small: establish Project as the
canonical operational layer, add stable references and prepare later migration.
